# ThreadSanitizer suppressions for the ikd-Tree concurrency tests
# (resple/test/test_ikdtree_concurrency.cpp) AND the Phase 6.1 sanitizer bag
# replay (scripts/sanitizer_replay.sh).
#
# Usage:
#   TSAN_OPTIONS="suppressions=$PWD/resple/test/tsan_suppressions.txt" <test-binary>
#
# Contains NO RESPLE-code suppressions — the gate must fail on any race in our
# own code. The only entries are third-party middleware races (see below).
#
# History:
# - Phase 2.5 #2 (working_flag_mutex <-> search_rw_mutex_ lock-order
#   inversion): FIXED; its `deadlock:` suppressions were removed so a
#   regression fails the gate.
# - Phase 2.5 #1 (background rebuild thread vs concurrent mutator on
#   KD_TREE_NODE fields — father_ptr / range arrays / alpha_* pull-up writes
#   vs the rebuild's father_ptr read + swap ancestor Update-walk): FIXED.
#   working_flag_mutex is now recursive and the public mutators hold it
#   across their whole operation (see ikd_Tree.cpp start_thread /
#   ScopedPthreadLock). The former `race:multi_thread_rebuild` /
#   `race:multi_thread_ptr` suppressions were removed; the
#   IkdTreeConcurrency.RebuildVsMutatorRace stress now runs TSan-clean with
#   no suppressions (pre-fix it reports ~200 races), so any regression fails.
#
# Do NOT add Search / Push_Down / multi_thread_rebuild entries here: those
# are exactly what the tests guard (Phase 2.4 reader-vs-reader and Phase
# 2.5 rebuild-path races). New suppressions need a HARDENING.md entry
# explaining why the underlying race is acceptable.

# --- External middleware (NOT RESPLE code) --------------------------------
# Fast-DDS (rmw_fastrtps_cpp — the osrf/ros image + CI default RMW) races its
# OWN payload pool between the publish-time serialize and a receive/statistics
# thread's deserialize: eprosima::fastcdr::Cdr::(de)serialize_array over a
# fastrtps TopicPayloadPool / StatisticsListenersImpl buffer. Surfaced by the
# Phase 6.1 LIO bag replay (HelmDyn01); reproduces with ZERO RESPLE
# involvement (publish() -> DDS internals). The production deployment uses
# rmw_zenoh, where this Fast-DDS path does not exist. Suppressed so the gate
# measures RESPLE code, not the DDS vendor. See HARDENING.md §6.1.
#
# Deliberately anchored on the DESERIALIZE side only. TSan suppresses a report
# if any frame of either stack matches, and the vendor race always carries the
# receive/statistics thread's deserialize frame — so this one entry silences
# it. A generic serialize_array entry was removed on purpose: "racing a
# serialize" is also the signature of a REAL bug class (RESPLE mutating a
# message while publish() serializes it), and that report would carry
# serialize_array but NOT deserialize_array, so it now fails the gate instead
# of being swallowed. If a new vendor-only serialize-side variant ever shows
# up, add it back anchored on a frame that cannot contain RESPLE code, with a
# HARDENING.md entry.
race:eprosima::fastcdr::Cdr::deserialize_array
